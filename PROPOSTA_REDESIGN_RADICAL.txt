PROBLEMA 1 — BASE TEMPLATE INVIÁVEL
  O arquivo templates/temp_base/adm.html possui 970 linhas com o sidebar
  inteiro REPETIDO 3 vezes dentro de blocos {% if user.is_administrator %},
  {% elif user.is_professor %} e {% else %} (escola). Isso significa que
  qualquer alteração no layout requer edição em 3 lugares simultâneos.
  Impossível manter, impossível escalar, impossível auditar.

PROBLEMA 2 — TECNOLOGIA OBSOLETA
  pcoded admin theme, waves.js, jquery-slimscroll, themify-icons, Bootstrap 3.
  Essas bibliotecas têm entre 8-12 anos sem manutenção ativa. O resultado visual
  é imediatamente reconhecido como "sistema de governo antigo" — exatamente
  o oposto do posicionamento premium desejado.

PROBLEMA 3 — MIGRAÇÃO FANTASMA INCOMPLETA
  Cada app tem DOIS diretórios de templates: templates/ e templates1/
  A migração para a nova versão (templates1/) está incompleta. Existe
  código morto em todo o projeto. Isso cria confusão sobre qual template
  está sendo usado em produção.

PROBLEMA 4 — DASHBOARDS FANTASMAS
  aluno_dash.html: literalmente "<h2>PAINEL ALUNO</h2>"
  funcionario_dash.html: literalmente "<h2>PAINEL FUNCIONARIO</h2>"
  Dois perfis de usuário sem nenhuma tela funcional.

PROBLEMA 5 — ZERO DESIGN SYSTEM
  Não existe linguagem visual consistente. Botões em diferentes estilos
  entre telas. Tabelas sem padrão. Sem estados vazios. Sem skeleton loading.
  Sem feedback visual de ações. Sem badges consistentes.

PROBLEMA 6 — NAVEGAÇÃO ESTRUTURADA COMO LISTA DE LINKS
  O menu atual é uma lista de submenu estilo "Adicionar X / Lista X" para
  cada entidade. Não existe agrupamento por contexto de trabalho. Um diretor
  de escola precisa percorrer 8+ itens de menu para fazer tarefas comuns.

PROBLEMA 7 — FORMULÁRIOS LONGOS E LINEARES
  Os formulários de cadastro (cadastramento.html, endereco.html,
  profissional.html) são sequenciais sem agrupamento visual. Formulários
  multi-step sem indicador de progresso. Alta taxa de abandono esperada.

PROBLEMA 8 — TABELAS QUE PARECEM PLANILHAS
  lista_avaliacoes.html, lista_questoes.html, lista_funcionarios.html —
  tabelas Bootstrap simples sem filtros, sem busca integrada, sem ações
  contextuais, sem seleção múltipla, sem estados de carregamento.

PROBLEMA 9 — HIERARQUIA DE INFORMAÇÃO AUSENTE
  Não há separação visual entre título de página, ações primárias e
  conteúdo. Tudo compete pela atenção do usuário com o mesmo peso visual.

PROBLEMA 10 — RESPONSIVIDADE IMPROVISADA
  O pcoded theme tem breakpoints do Bootstrap 3. Em dispositivos modernos
  (especialmente tablets usados por coordenadores em campo), a experiência
  está quebrada.

PRINCÍPIO DO BASE TEMPLATE ÚNICO:
  _base.html extende NADA.
  app.html extende _base.html e inclui _sidebar.html + _topbar.html.
  _sidebar.html usa {% include partials/_nav_PERFIL.html %} baseado no perfil.
  Cada tela de app extende app.html e sobrescreve apenas {% block content %}.

TIPOGRAFIA:
  Font-family: "Inter", system-ui, -apple-system, sans-serif
  Escala:
    text-xs   → 11px (labels, badges, metadados)
    text-sm   → 13px (conteúdo de tabelas, inputs)
    text-base → 15px (corpo de texto padrão)
    text-lg   → 17px (títulos de card)
    text-xl   → 20px (títulos de seção)
    text-2xl  → 24px (título de página)
    text-3xl  → 30px (métricas de dashboard)

ESPAÇAMENTO:
  Sidebar: w-64 (256px) fixo no desktop, collapsible no tablet
  Topbar: h-14 (56px)
  Padding de página: px-6 py-6 (desktop), px-4 py-4 (mobile)
  Gap entre cards: gap-4 ou gap-6
  Padding interno de card: p-5 ou p-6

ELEVAÇÃO (sombras discretas):
  Level 0: nenhuma sombra (itens inline)
  Level 1: shadow-sm (cards padrão)
  Level 2: shadow-md (modais, dropdowns)
  Level 3: shadow-lg (sidebar ao colapsar sobre conteúdo)

BORDAS:
  Radius padrão: rounded-xl (12px) para cards
  Radius pequeno: rounded-lg (8px) para inputs, badges, botões
  Radius total: rounded-full para avatares, chips de status

ÍCONES:
  Usar Heroicons via CDN (heroicons.com) ou SVG inline copiado.
  Padrão de tamanho: w-4 h-4 (inline em texto), w-5 h-5 (botões), w-6 h-6 (nav)
  Nunca usar icon fonts (themify, font-awesome) — causam FOUT e têm acessibilidade ruim.

JAVASCRIPT:
  Mínimo de JS. Usar Alpine.js (CDN) APENAS quando necessário:
  - Dropdowns não nativos
  - Toggles de sidebar mobile
  - Toast de messages com auto-dismiss
  - Modais de confirmação simples

  Não usar jQuery. Não usar nenhum plugin jQuery.
  Para comportamentos complexos (Drag&Drop em questões): usar SortableJS (standalone, sem jQuery).

DJANGO + HTMX (OPCIONAL MAS RECOMENDADO):
  Considerar adicionar HTMX para:
  - Busca em tabelas sem reload (hx-get + hx-trigger="keyup changed delay:300ms")
  - Modais de confirmação inline
  - Registro de frequência sem reload de página
  Isso eliminaria a maioria das necessidades de Alpine.js e reduziria JS a zero em muitas telas.

  Criar widget customizado para todos os campos:
  class TailwindInput(TextInput):

          kwargs['attrs'].update({'class': 'input input-bordered w-full'})
          super().__init__(*args, **kwargs)

ISSO REALMENTE PARECE UM PRODUTO PREMIUM?
  Sim — a combinação de Inter + azul royal + emerald para sucesso + fundo
  slate claro com cards brancos é exatamente o vocabulário visual de
  produtos como Linear, Vercel e Clerk. É sóbrio, rápido de escanear e
  transmite profissionalismo sem ser genérico.

ISSO PARECE PRONTO PARA VENDER?
  Com as Fases 1-3 implementadas: sim. Um diretor de escola compraria
  imediatamente ao ver o dashboard com frequência visual de turmas +
  registro em 3 cliques.

ISSO É MELHOR QUE UM CRUD COMUM?
  Significativamente. A diferença está em:
  - Dashboard que antecipa ações (turma sem frequência = CTA proeminente)
  - Registro de frequência com "marcar todos presentes" em 1 clique
  - Wizard de avaliação guiado vs 3 formulários separados
  - Status visual por cor nas turmas/salas

EXISTE ALGO QUE AINDA PODE SER REFINADO?
  Sim — duas áreas que merecem atenção na implementação:

  1. CONTEXTO MULTIESCOLA NO ADMIN CENTRAL:
     O seletor de escola na topbar do admin precisa ser muito bem
     implementado. O admin muda de "contexto de escola" e todas as
     URLs precisam refletir isso corretamente. Proposta: usar sessão
     Django para armazenar "escola ativa" do admin, com middleware
     que injeta no request. Isso elimina a necessidade de slug em
     todas as URLs.

  2. MODO OFFLINE / PWA PARA PROFESSORES:
     Professores em escolas rurais podem não ter internet constante.
     Registrar frequência deve funcionar offline. Fase 6 (PWA) deve
     ser planejada desde a Fase 1 para não criar dívida técnica.
     Implementar: service worker com cache de tela de registro +
     IndexedDB para fila de sincronização.
