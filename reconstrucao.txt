PRODUTO
  Nome:             EduCare
  Tipo:             SaaS B2B multi-escola (multi-tenant row-level)
  Foco:             Gestão escolar — ensino fundamental/médio

STACK
  Linguagem:        Python 3.13
  Framework:        Django 6.0 (última estável)
  Frontend:         Server-side rendering (Django Templates) — sem framework JS pesado
  CSS / Componentes: Tailwind CSS v4 (CDN) + Flowbite
  Ícones:           Lucide Icons (via CDN)
  DB Desenvolvimento: SQLite
  DB Produção:      MySQL (adapter a definir futuramente)
  Billing:          Mercado Pago
  PDF:              WeasyPrint (renderiza templates HTML → PDF)
  Excel:            openpyxl
  Imagens:          Pillow
  Variáveis de env: django-environ
  Testes:           pytest-django
  Linting/Format:   Ruff
  Arquivos estáticos (prod): Whitenoise
  Pacotes:          pip + requirements.txt
  WhatsApp:         Envios manuais por enquanto (provider a integrar futuramente)

ARQUITETURA DE TEMPLATES
  Cada tipo de usuário possui seu próprio template pai.
  Padrão visual baseado no layout atual de escola/diretor.
  Renderização server-side (Django Templates) — sem framework JS pesado.
  Templates pai por tipo:
    base/base_plataforma.html   → Super Admin (EduCare)
    base/base_diretor.html      → Diretor
    base/base_funcionario.html  → Funcionário
    base/base_professor.html    → Professor
    base/base_aluno.html        → Aluno
    base/base_responsavel.html  → Responsável

MULTI-TENANCY
  Estratégia:   Row-level (dados isolados por escola no mesmo banco/schema)
  Identificação do tenant por sessão: request.session['papel_id']
  Injeção no request: request.papel + request.vinculo + request.escola

[ 00 ] CORE
-----------
  Status:      [ DECISÕES VALIDADAS — aguardando implementação ]
  Descrição:   Fundação do sistema. Modelo de usuário, middleware de tenant,
               sistema de permissões, templates pai, autenticação.
  Depende de:  —
  Bloqueia:    Todos os outros módulos

  DECISÕES VALIDADAS:

  [MODELOS]
  · Usuario — AbstractBaseUser + PermissionsMixin. Login por email. Campos
    pessoais apenas (nome, foto, is_active). Flag is_platform_admin para
    o Super Admin do EduCare (não pertence a nenhuma escola).

  · VinculoEscola — liga Usuario a Escola. Um registro por par (usuario+escola).
    unique_together = ('usuario', 'escola'). Campos: ativo, data_entrada.
    Um usuário pode ter vínculos com múltiplas escolas (N registros).

  · PapelVinculo — os papéis do usuário dentro de um vínculo.
    FK para VinculoEscola. unique_together = ('vinculo', 'tipo').
    Campos: tipo (TipoVinculo), ativo.
    Um vínculo pode ter múltiplos papéis (ex: DIRETOR + PROFESSOR).

  · TipoVinculo (TextChoices): DIRETOR, FUNCIONARIO, PROFESSOR, ALUNO,
    RESPONSAVEL.

  [MIDDLEWARE]
  · Renomear EscolaMiddleware → TenantMiddleware.
  · Sessão guarda papel_id (PapelVinculo.id), não escola_id.
  · Injeta: request.papel, request.vinculo, request.escola.
  · Fluxo pós-login:
      0 vínculos ativos            → logout
      1 escola · 1 papel           → dashboard direto
      1 escola · N papéis          → tela seleção de papel
      N escolas                    → tela seleção de escola
        └─ escola com 1 papel      → dashboard direto
        └─ escola com N papéis     → tela seleção de papel

  [SERVICE LAYER]
  · Nenhuma view toca modelos de usuario/vinculo diretamente.
  · core/services/usuario_service.py — criar, editar, desativar, trocar email.
  · core/services/vinculo_service.py — criar vínculo, adicionar papel,
    remover papel, listar vínculos ativos, selecionar papel ativo.
  · Todas as operações com @transaction.atomic.

  [PERMISSÕES]
  · PermissaoRequiredMixin verifica request.papel.tipo contra lista da view.
  · BaseDashboardView garante autenticação + papel na sessão + tipo permitido.

  [TEMPLATES PAI]
  · Ver seção ARQUITETURA DE TEMPLATES nas decisões globais.
  · Cada view herda do template pai do tipo do request.papel ativo.

  [MODULARIZAÇÃO — definida antes de Planos/Assinatura]
  · O sistema é modularizado: cada módulo pode ser ativado/desativado
    por escola sem comprometer os demais.
  · Três camadas de controle:
      Plataforma  → define quais módulos existem (kill-switch global)
      Plano       → define quais módulos estão incluídos no plano
      Escola      → pode DESATIVAR módulos do plano (não ativar além dele)
  · Modelos:
      Modulo(codigo, nome, ativo_plataforma)
      Plano(nome, preco_mensal, modulos M2M, limite_alunos, limite_turmas)
      AssinaturaEscola(escola 1-1, plano, status, data_inicio, data_fim)
        status choices: TRIAL, ATIVA, SUSPENSA, CANCELADA
      ModuloEscola(assinatura, modulo, ativo)
  · Códigos de módulo são constantes Python em core/modulos.py (CodigoModulo)
    — nunca strings mágicas espalhadas no código.
  · Módulos opcionais (podem ser desativados por escola):
      financeiro_escolar, frequencia, avaliacoes, boletim,
      comunicados, relatorios, responsaveis
  · Módulos obrigatórios (sempre ativos — fazem parte do Core):
      escola, diretor, funcionarios, professores, alunos, turmas, series
  · Mixin ModuloRequiredMixin: toda view de módulo opcional declara
    modulo_codigo e o mixin verifica ativação antes de despachar.
  · Módulos são criados via data migration usando as constantes de CodigoModulo.


[ 01 ] PLANOS / ASSINATURA SAAS
--------------------------------
  Status:      [ DECISÕES VALIDADAS — aguardando implementação ]
  Descrição:   Gestão de assinaturas das escolas no EduCare. Planos definidos
               por módulos ativos. Ativação manual pelo Super Admin.
               Sem integração de gateway de pagamento neste módulo.
               Inclui o sistema de módulos (Modulo, ModuloEscola).
               Distinto do Financeiro Escolar.
  Depende de:  Core
  Bloqueia:    Onboarding, limites por plano em todos os módulos

  DECISÕES VALIDADAS:

  [FLUXO DE ATIVAÇÃO]
  · Sem automação de pagamento neste módulo — pagamento é tratado fora
    do sistema. Super Admin confirma e ativa manualmente.
  · Upgrade/downgrade somente via suporte (não self-service).

  [MODELOS]
  · Plano(nome, descricao, preco_mensal, modulos M2M, ativo)
      ativo → desativa da venda sem excluir histórico
      modulos → ManyToMany(Modulo) — plano é definido por módulos, não por limites

  · AssinaturaEscola(escola 1-1, plano FK null, status, campos de trial,
      campos de assinatura ativa, campos de grace, ativado_por, atualizado_em)
      plano → null durante trial
      data_inicio_trial, limite_alunos_trial=30, duracao_trial_dias=10
      data_inicio, data_vencimento, data_grace_fim (null fora do contexto)
      ativado_por → FK(Usuario) — Super Admin que ativou

  · HistoricoAssinatura(assinatura, status_anterior, status_novo,
      plano_anterior null, plano_novo null, alterado_por, alterado_em, observacao)
      Registro imutável de toda mudança de status ou plano.

  · SEM modelo de pagamento — Super Admin gerencia status diretamente.

  [STATUS — com propósito comercial distinto]
  · TRIAL          → nunca pagou, dentro dos limites (alunos E prazo)
  · TRIAL_EXPIRADO → nunca pagou, saiu dos limites — lead de vendas
  · ATIVA          → pagou, dentro do prazo
  · GRACE          → prazo venceu, carência de 15 dias — risco de churn
  · SUSPENSA       → grace venceu, bloqueio total — churn confirmado
  · CANCELADA      → encerramento deliberado

  [TRIAL]
  · Limite: 30 alunos ativos OU 10 dias — o que vencer primeiro.
  · Contagem: apenas alunos com ativo=True (inativos/transferidos não contam).
  · Todos os módulos ativos durante o trial (escola experimenta o produto completo).
  · Transição de TRIAL → TRIAL_EXPIRADO disparada em dois pontos:
      AlunoService.criar() — verifica limite de alunos após cada criação
      Management command diário — verifica limite de dias

  [GRACE PERIOD]
  · Duração: 15 dias após vencimento da assinatura ativa.
  · Acesso: total (escola ainda funciona normalmente).
  · Alertas: D+0, D+5, D+10, D+14, D+15.
  · Ao vencer: status → SUSPENSA, bloqueio total.
  · Transição disparada pelo management command diário.

  [ACESSO POR STATUS — verificado no TenantMiddleware]
  · TRIAL          → trial_valido()? acesso total : redireciona tela trial expirado
  · ATIVA          → acesso total
  · GRACE          → acesso total + banner de alerta persistente
  · TRIAL_EXPIRADO → bloqueio total
  · SUSPENSA       → bloqueio total
  · CANCELADA      → bloqueio total

  [TAREFAS AGENDADAS]
  · Management command diário (não Celery — overengineering para o estágio atual).
  · Arquitetura preparada para migrar para Celery futuramente sem reescrever lógica.
  · Responsabilidades do command:
      - Transicionar TRIAL → TRIAL_EXPIRADO (limite de dias atingido)
      - Transicionar ATIVA → GRACE (data_vencimento atingida)
      - Transicionar GRACE → SUSPENSA (data_grace_fim atingida)
      - Disparar alertas de grace (D+0, D+5, D+10, D+14, D+15)

  [SERVICE LAYER]
  · planos/services/assinatura_service.py
      trial_valido(assinatura) → bool
      ativar(assinatura, plano, data_vencimento, usuario) → @transaction.atomic
        cria/recria registros ModuloEscola conforme módulos do plano
      iniciar_grace(assinatura, usuario) → @transaction.atomic
      suspender(assinatura, usuario) → @transaction.atomic
      cancelar(assinatura, usuario) → @transaction.atomic
      Todos registram em HistoricoAssinatura.

  [FORMULÁRIOS — Super Admin / base_plataforma.html]
  · PlanoForm             → criar/editar plano (módulos via CheckboxSelectMultiple)
  · AssinaturaAtivarForm  → plano + data_vencimento + observação
  · AssinaturaGraceForm   → iniciar grace manualmente + observação
  · AssinaturaSuspenderForm → suspender + observação


[ 02 ] ONBOARDING
-----------------
  Status:      [ IMPLEMENTADO — 2026-06-26 ]
  Descrição:   Fluxo de entrada de nova escola. Super Admin cria a escola,
               Diretor recebe convite e completa o cadastro.
  Depende de:  Core, Planos/Assinatura
  Bloqueia:    Escala da plataforma

  DECISÕES VALIDADAS:

  [FLUXO — HÍBRIDO (SUPER ADMIN CRIA, DIRETOR COMPLETA)]
  · Passo 1 — Super Admin cria escola:
      Preenche: nome da escola, CNPJ, email e telefone do Diretor
      EscolaService.criar() → cria UnidadeEscolar + AssinaturaEscola(TRIAL)
      Sistema gera ConviteOnboarding + link tokenizado
      Super Admin escolhe canal de envio: email ou WhatsApp

  · Passo 2 — Diretor acessa o link do convite:
      Define senha + completa perfil (PerfilDiretor criado)
      Token marcado como usado=True — link invalidado

  · Passo 3 — Primeiro acesso ao dashboard:
      Checklist de configuração inicial exibido no dashboard:
        [ ] Adicionar segmentos de ensino
        [ ] Configurar séries
        [ ] Criar ano letivo
        [ ] Configurar parâmetros acadêmicos
      Checklist é visual e não-obstrutivo — Diretor configura no próprio ritmo

  [MODELO]
  · ConviteOnboarding(escola FK, email, telefone null, token uuid,
        canal_envio, usado bool, criado_em, expira_em)
      canal_envio → CanalConvite: EMAIL, WHATSAPP
      token → uuid4, gerado automaticamente
      expira_em → criado_em + 72 horas
      usado → True após primeiro acesso — link não funciona mais
      Reenvio invalida o convite anterior (usado=True no anterior)

  [CANAIS DE ENVIO DO CONVITE]
  · Email   → envio automático pelo sistema
  · WhatsApp → link gerado pelo sistema, entregue via provider de WhatsApp
      Provider a definir: Z-API, Evolution API, Twilio ou similar
      Arquitetura preparada para automação — sem bloquear o design atual

  [CHECKLIST DE CONFIGURAÇÃO INICIAL]
  · Exibido no dashboard do Diretor até todos os itens serem concluídos.
  · Itens verificados em tempo real (queries — sem modelo extra).
  · Dispensável pelo Diretor a qualquer momento.

  [PERMISSÕES]
  · Criar escola + gerar convite:     APENAS Super Admin
  · Completar perfil e configurações: Diretor (via link do convite)

  [SERVICE LAYER]
  · onboarding/services/onboarding_service.py
      criar_escola_e_convite(dados, canal_envio, criado_por) → @transaction.atomic
        chama EscolaService.criar() + cria ConviteOnboarding + envia convite
      reenviar_convite(escola, canal_envio) → invalida anterior + cria novo + envia
      validar_token(token) → ConviteOnboarding ou raise erro
      completar_onboarding(token, senha, perfil_dados) → @transaction.atomic
        define senha do Usuario + cria PerfilDiretor + marca convite como usado

  · ConfiguracaoFinanceira → definida no módulo Financeiro Escolar (módulo 19)

  [PERMISSÕES — APENAS DIRETOR]
  · Editar qualquer configuração da escola:   APENAS DIRETOR
  · Visualizar:                               DIRETOR + COLABORADOR (leitura)

  [SERVICE LAYER]
  · configuracao/services/configuracao_service.py
      criar_configuracoes_padrao(escola) → chamado por EscolaService.criar()

        com todos os valores padrão
      atualizar_academica(escola, dados)

  · In-app apenas por ora — sininho no topo do layout, lista de notificações.

      tipo → TipoNotificacao: ACADEMICA, FINANCEIRA, COMUNICADO, SISTEMA

[ 05 ] AUDITORIA
----------------
  Status:      [ IMPLEMENTADO — 2026-06-29 ]
  Descrição:   Log imutável de ações críticas por usuário. Quem fez o quê,
               quando e de qual escola. Requisito B2B com dados de menores.
  Depende de:  Core
  Bloqueia:    —

  DECISÕES VALIDADAS:

  [ESCOPO — APENAS AÇÕES CRÍTICAS]
  · Registradas explicitamente no service — sem middleware automático.
  · Ações que geram log: criação/edição/desativação de aluno, lançamento de
    nota, mudança de matrícula, alterações financeiras, mudanças de senha,
    login, logout, alterações de assinatura, criação de usuários.
  · Ações rotineiras (leituras, filtros, navegação) não são registradas.

  [MODELO]
  · LogAuditoria(usuario FK Usuario null, escola FK Escola null,
        papel_tipo, acao, modelo, objeto_id,
        descricao, ip, criado_em)
      usuario → null quando ação é de sistema (management command)
      escola  → null para ações da plataforma (Super Admin)
      papel_tipo → tipo do papel ativo no momento da ação
      acao → AcaoAuditoria: CRIAR, EDITAR, DESATIVAR, REATIVAR, LOGIN, LOGOUT
      modelo → nome do model afetado (ex: "Aluno", "MatriculaTurma")
      objeto_id → PK do objeto afetado
      descricao → texto livre descrevendo a mudança
                  (ex: "Turma alterada de 6A para 6B")
      ip → capturado do request

  [IMUTABILIDADE E RETENÇÃO]
  · LogAuditoria nunca é editado ou deletado — apenas criado.
  · Sem soft delete — sem campo ativo.
  · Retenção: 5 anos (dado de menor de idade — obrigação legal brasileira).

  [VISIBILIDADE]
  · Super Admin    → todos os logs da plataforma
  · Diretor        → apenas logs da sua escola
  · Demais papéis  → sem acesso

  [SERVICE LAYER]
  · auditoria/services/auditoria_service.py
      registrar(request, acao, objeto, descricao) → cria LogAuditoria
        captura usuario, escola e papel_tipo do request automaticamente
        objeto_id e modelo extraídos do objeto passado
      listar_escola(escola, filtros) → queryset paginado para o Diretor
      listar_plataforma(filtros) → queryset paginado para o Super Admin

  Status:      [ IMPLEMENTADO — 2026-06-29 ]
  Descrição:   Pais e responsáveis vinculados a alunos. Acesso a boletim,

        parentesco, responsavel_financeiro bool, responsavel_principal bool, ativo)
      parentesco → Parentesco: PAI, MAE, AVO, TIO, TIA, RESPONSAVEL_LEGAL, OUTRO
        (vive aqui — é a relação com o filho, não com a escola)
      responsavel_financeiro → recebe cobranças do módulo Financeiro Escolar
      responsavel_principal → contato prioritário para comunicados e notificações
      UniqueConstraint(fields=['aluno'], condition=Q(responsavel_principal=True))
        garante no banco: apenas um responsável principal por aluno

  [MULTI-ESCOLA — RESPONSÁVEL COM FILHOS EM ESCOLAS DIFERENTES]
  · Responsável pode ter filhos em N escolas diferentes.
  · No login: TenantMiddleware detecta N VinculoEscola e exibe tela de seleção
    de escola (já coberto pelo fluxo validado no Core).
  · Verificador ao cadastrar em nova escola:
      1. Busca Usuario por CPF ou email
      2. Encontrado → cria apenas VinculoEscola + PapelVinculo(RESPONSAVEL)
           sem novo PerfilResponsavel
      3. Não encontrado → cria Usuario + PerfilResponsavel + VinculoEscola
           + PapelVinculo(RESPONSAVEL)

  [LOGIN OPCIONAL]
  · Responsável pode ser cadastrado sem Usuario (contato puro — sem acesso ao sistema).
  · Nesse caso: PerfilResponsavel.usuario = null.
  · Acesso ao sistema ativado posteriormente quando necessário:
      responsavel_service.ativar_acesso(perfil, email) → cria Usuario + VinculoEscola
        + PapelVinculo(RESPONSAVEL) e vincula ao PerfilResponsavel existente.

  [VISIBILIDADE]
  · Responsável vê apenas: boletim dos seus filhos, comunicados da escola,
    financeiro dos seus filhos. Nada além disso.
  · Não vê outros alunos, professores, turmas completas ou dados administrativos.

  [PERMISSÕES]
  · Cadastrar responsável:                    DIRETOR + COLABORADOR
  · Vincular responsável a aluno:             DIRETOR + COLABORADOR
  · Editar próprio perfil:                    o próprio RESPONSAVEL
  · Editar perfil de outro:                   DIRETOR + COLABORADOR
  · Desativar:                                DIRETOR + COLABORADOR
  · Visualizar lista:                         DIRETOR + COLABORADOR

  [SERVICE LAYER]
  · responsavel/services/responsavel_service.py
      criar(escola, usuario_dados, perfil_dados, criado_por) → @transaction.atomic
        verifica Usuario existente por CPF ou email antes de criar
        se encontrado: reutiliza Usuario + PerfilResponsavel, cria só VinculoEscola
        se não encontrado: cria Usuario + PerfilResponsavel + VinculoEscola
        em ambos os casos: cria PapelVinculo(RESPONSAVEL)
      criar_sem_acesso(escola, perfil_dados, criado_por) → @transaction.atomic
        cria PerfilResponsavel sem Usuario (usuario=null)
      ativar_acesso(perfil, email) → cria Usuario + VinculoEscola + PapelVinculo
      vincular_aluno(perfil, aluno, dados) → cria VinculoResponsavelAluno
      editar(perfil, dados)
      desativar(papel_vinculo, desativado_por)

  · Plano ativo: respeita plano.limite_alunos.

      unique_together: ('avaliacao', 'aluno')

      ausente → registra falta na avaliação (distinto de nota zero)

  · Professor cria Avaliacao(ONLINE) + Questoes + OpcaoResposta

  · Regra aplicada pelo BoletimService ao consolidar notas do período
  · Configurada em ConfiguracaoAcademica (exige_recuperacao, nota_minima_recuperacao)

  [PERMISSÕES]
  · Criar avaliação:          PROFESSOR (suas turmas/matérias) + DIRETOR
  · Lançar/corrigir notas:   PROFESSOR (suas turmas/matérias) + DIRETOR
  · Gerar PDF:                PROFESSOR + DIRETOR
  · Ver avaliações e notas:  DIRETOR + COLABORADOR (leitura, sempre)
                              ALUNO + RESPONSÁVEL (apenas quando publicada=True)

  [SERVICE LAYER]
  · avaliacao/services/avaliacao_service.py
      criar(dados, questoes, criado_por) → @transaction.atomic
      publicar(avaliacao) / despublicar(avaliacao)
      gerar_pdf(avaliacao) → PDF com questões formatadas
      submeter_respostas(avaliacao, aluno, respostas) → @transaction.atomic
        cria RespostaAluno + autocorrige MC + verifica se todas corrigidas
      corrigir_discursiva(resposta, nota_questao, professor) → @transaction.atomic
        salva nota + verifica se todas corrigidas → calcula NotaAluno se completo
      lancar_nota_manual(avaliacao, aluno, nota, ausente) → NotaAluno (PRESENCIAL)
      lancar_notas_em_massa(avaliacao, lista_notas) → @transaction.atomic

  Status:      [ IMPLEMENTADO — 2026-06-29 ]
  Descrição:   Registro de presença/ausência por aula. Lançamento diário,
               semanal ou mensal conforme configuração da escola. Dois níveis
               de alerta de infrequência. Alimenta o Boletim.
  Depende de:  Core, Turmas, Alunos, Professores, Matérias, Configurações
  Bloqueia:    Boletim (percentual de frequência), Relatórios

  DECISÕES VALIDADAS:

  [GRANULARIDADE]
  · Registro por aula — não por dia.
  · Mais preciso para cálculo legal (75% das aulas ministradas).
  · Professor de Matemática com 2 aulas/semana registra 2 presenças separadas.

  [MODELOS]
  · RegistroFrequencia(turma FK, materia FK null, professor FK,
        data, periodo_aula FK null, ano_letivo FK, criado_em)
      materia → null no modo ProfessorTurma (INF/FI)
      periodo_aula → null se escola não usar grade horária cadastrada

  · PresencaAluno(registro FK, aluno FK, presente bool,
        justificado bool, observacao null)
      unique_together: ('registro', 'aluno')
      justificado → falta com justificativa (conta como falta, visível no boletim)

  [MODO DE LANÇAMENTO — CONFIGURADO PELA DIREÇÃO]
  · O modelo de dados não muda — RegistroFrequencia sempre é por aula/dia.
  · O que muda é a interface de lançamento, definida em
    ConfiguracaoFrequencia.modo_lancamento:
      DIARIO   → professor registra dia a dia (padrão)
      SEMANAL  → professor abre grade semanal e preenche os 5 dias de uma vez
      MENSAL   → professor preenche o mês inteiro retroativamente de uma vez
  · Dados armazenados de forma idêntica em todos os modos —
    relatórios e cálculos são consistentes independente do modo escolhido.

  [ALERTAS DE INFREQUÊNCIA — DOIS NÍVEIS]
  · Campos em ConfiguracaoFrequencia:
      percentual_alerta_prevencao  → Decimal (padrão: 80.0)
      percentual_minimo_frequencia → Decimal (padrão: 75.0)
  · Ao atingir percentual_alerta_prevencao:
      notificação amarela para Diretor + Responsável (aviso preventivo)
  · Ao cair abaixo de percentual_minimo_frequencia:
      notificação vermelha urgente para Diretor + Responsável (risco de reprovação)
  · Verificação disparada a cada PresencaAluno salva.

  [FALTA COLETIVA]
  · Aula que não ocorreu → Diretor ou Colaborador cancela o RegistroFrequencia.
  · Remoção do registro elimina todas as PresencaAluno vinculadas.
  · Não gera registros de presença para aulas que não aconteceram.

  [PERMISSÕES]
  · Registrar frequência:    PROFESSOR (suas turmas/matérias) + DIRETOR
  · Justificar falta:        PROFESSOR (suas turmas) + DIRETOR + COLABORADOR
  · Cancelar aula:           DIRETOR + COLABORADOR
  · Ver frequência:          DIRETOR + COLABORADOR (todos os alunos)
                             PROFESSOR (alunos das suas turmas)
                             ALUNO (própria frequência, quando tiver login)
                             RESPONSÁVEL (frequência dos filhos)

  [SERVICE LAYER]
  · frequencia/services/frequencia_service.py
      criar_registro(turma, materia, professor, data, periodo_aula, ano_letivo)
      lancar_presencas(registro, lista_presencas) → @transaction.atomic
        salva PresencaAluno + dispara verificação de alertas
      justificar_falta(presenca, observacao, usuario)
      cancelar_aula(registro, usuario) → remove RegistroFrequencia + PresencaAluno
      calcular_percentual(aluno, materia, periodo_letivo) → Decimal
      verificar_alertas(aluno, materia, periodo_letivo) → dispara notificações
        se necessário (dois níveis: prevenção e mínimo)

  [CATÁLOGO DE RELATÓRIOS]

  Pedagógico:
  · Desempenho por turma/matéria/período
      médias, % aprovados, % em recuperação, % reprovados
  · Frequência consolidada por turma ou por aluno
  · Alunos em risco (baixa nota + baixa frequência combinados)
  · Boletim em lote — PDF de todos os alunos de uma turma de uma vez

  Gestão (APENAS DIRETOR):
  · Desempenho por professor
      média das turmas por matéria e por professor
      sinaliza quando ≥50% dos alunos estão abaixo da nota mínima em uma turma
      sinaliza padrão repetido em múltiplas turmas do mesmo professor
        (indicador de qualidade de ensino — dado sensível, exclusivo do Diretor)
      NÃO visível para o Professor

  Administrativo:
  · Inadimplência — cobranças vencidas por aluno/turma/período
  · Extrato financeiro por período

  [GERAÇÃO — SOB DEMANDA + AGENDADA]

  Sob demanda:
  · Diretor/Colaborador aplica filtros e gera na hora
  · Resultado renderizado on-screen antes de exportar (sem download obrigatório)
  · Exportação em PDF ou Excel (.xlsx)

  Agendada:
  · RelatorioAgendado(escola FK, tipo, periodicidade, parametros JSON, ativo)
      periodicidade → PeriodicidadeRelatorio: MENSAL, POR_PERIODO, ANUAL
      parametros → JSON com filtros (turma, materia, etc.)
  · RelatorioGerado(agendado FK null, escola FK, tipo, parametros JSON,
        arquivo FileField, gerado_em)
      arquivo → salvo em media/relatorios/escola_id/
      ao gerar: notificacao_service.criar() para o Diretor
  · Management command executa relatórios agendados no momento configurado
    (mesmo padrão de Planos e Financeiro — sem Celery por ora)

  [FORMATOS DE EXPORTAÇÃO]
  · PDF     → WeasyPrint ou ReportLab — com identidade visual da escola
  · Excel   → openpyxl (.xlsx) — para análise e cruzamento externo
  · On-screen → renderizado em template antes de qualquer exportação

  [IMPLEMENTAÇÃO]
  · Sem modelo próprio para os dados — queries sobre dados existentes
  · Cada relatório: view com filtros + service que agrega + template renderizado
  · RelatorioAgendado e RelatorioGerado são os únicos modelos do módulo
